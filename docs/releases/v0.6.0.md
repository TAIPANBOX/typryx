# Typryx 0.6.0

A minor release, because the `openai-logprobs` backend gains three configuration variables. OpenAI retires `gpt-4.1-mini` and `gpt-4o-mini` on 2027-01-14 and has already shut `gpt-4.1-nano` down, and the models it names to replace them refuse the request this backend sent. From this release the backend reaches `gpt-6-luna`, `gpt-5.6-luna`, `gpt-6-sol` and `gpt-5.6-sol` with nothing in between.

## Upgrade

Pull `ghcr.io/taipanbox/typryx:v0.6.0` in place of `v0.5.1`. The stored state is the same. With none of the new variables set, the request is byte for byte what v0.5.1 sent, so a local server or an older hosted model needs no edit.

Two things differ from v0.5.1 on every deployment of this backend:

- **A deployment with `TYPRYX_MAX_USD_PER_DAY` can reach its cap sooner.** A reply the server billed and this backend could not use now counts against the cap. It did not before, so the cap read low.
- **Some replies that were `bad_logprobs` are now answers.** A logprob up to 0.001 above zero counts as rounding, where the bound used to be 0.000001. Anything above that is still refused.

## Moving to a current OpenAI model

```sh
TYPRYX_OPENAI_URL=https://api.openai.com/v1
TYPRYX_OPENAI_MODEL=gpt-6-luna
TYPRYX_OPENAI_TOP_LOGPROBS=5
TYPRYX_OPENAI_MAX_COMPLETION_TOKENS=16
TYPRYX_OPENAI_REASONING_EFFORT=none
```

These models report token probabilities only at `reasoning_effort: none`, refuse `max_tokens` by name, and refuse more than five alternatives. `gpt-4.1-mini` refuses `reasoning_effort` by name, so leave the three unset on a model that still takes the old request. `gpt-6.1-sol` refuses `reasoning_effort: none` and so cannot be reached by this backend. The README's [OpenAI's current models](https://github.com/TAIPANBOX/typryx#openais-current-models) has what each setting answers and what reads differently on these models.

## Added

- `TYPRYX_OPENAI_TOP_LOGPROBS`, from 1 to 20, default 20.
- `TYPRYX_OPENAI_MAX_COMPLETION_TOKENS`, from 1 to 256; set, the request carries `max_completion_tokens` in place of `max_tokens: 1`. The first token of a reply is still the only one read.
- `TYPRYX_OPENAI_REASONING_EFFORT`, one lowercase word, sent as `reasoning_effort`.
- A value out of range stops the service at start, naming the variable.

## Fixed

- **A near-certain answer was thrown away as `bad_logprobs` (#40).** OpenAI's current models report in steps of 2^-18, so an almost certain token can come back a few steps above zero. The old bound refused that: 13 of 60 answers on `gpt-5.6-luna`, ten of them on items whose answer was right.
- **A billed reply never reached the daily cap (#40).** The backend returned no usage on `no_logprobs`, `bad_logprobs` and `label_mass_too_low`. A body that does not parse still reports nothing, because no estimate stands in for a number the server did not send.

## Measured

The 60 calibration items through this backend, nothing in between, from a Linux host against the hosted API on 2026-11-06. Every run answered 60 of 60.

| Model | Accuracy / mean confidence |
|---|---|
| gpt-6-luna | 0.717 / 0.960, 0.733 / 0.976, 0.717 / 0.978 |
| gpt-5.6-luna | 0.650 / 0.967, 0.617 / 0.980, 0.600 / 0.984 |
| gpt-6-sol | 1.000 / 1.000 |
| gpt-5.6-sol | 1.000 / 1.000 |
| gpt-4.1-mini, nothing set | 0.750 / 0.984 |

The hosted API does not repeat itself, so two runs differ by a few items. The same 60 requests from v0.5.1 and from this code have one sha256, and over Ollama 0.40.14 with `qwen2.5:7b` the two binaries gave identical probabilities at the same position in a fresh container.
