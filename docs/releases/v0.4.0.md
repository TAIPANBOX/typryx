# Typryx 0.4.0

A starter template for the one question a risk policy asks, and a small
reverse proxy that puts typryx's answer to it in front of wardryx. Both are
optional add-ons: nothing changes for a deployment that uses neither. This
release was approved by the owner.

## Added

- **`action.risk_class` starter template (typryx#15).**
  `examples/templates/action.risk_class.json` is byte for byte the template
  `typryx-evalset` measured (SPEC family 5), so the evalset's numbers are
  numbers about the template that runs. It sends the tool name, the tool's
  arguments and its target, and nothing else. Two tests hold it: one to the
  evalset's copy, one to the three fields. `typryx templates check` now loads
  five starter templates.
- **`typryx wardryx-proxy` (typryx#17).** A reverse proxy between a caller
  (for example the TokenFuse MCP broker) and wardryx. It forwards every
  request to wardryx unchanged (method, path, query, headers including
  `Authorization`, body) and never alters wardryx's response; only
  `X-Typryx-Key` is removed on the way. The one exception is a
  `POST /v1/decide` whose JSON body carries a `tool_call` with a non-blank
  `name` and no `arguments_truncated`: typryx is asked in-process (egress
  filter, caps, ledger and journal all apply) from `tool`, `arguments` and
  `target` only, under a deadline, and a clean choice is appended as one
  `{name: "action.risk_class", value, probability, source: "typryx",
  answer_id}` entry after any existing `signals`. Anything else (no answer,
  a timeout, truncated arguments, an unusual body) forwards the original
  bytes untouched. If wardryx is unreachable the proxy answers 502 with a
  fixed body that names nothing, so the caller's own failure mode decides.
  Wardryx reads the signal through its `hold_if_signal` rule (wardryx
  v1.2.0), which can hold a call and nothing else.
- `scripts/one-way-out.sh` gains one named exception, `internal/wardryxproxy`
  (a transport to the one configured upstream), with teeth cases for the
  exception and for a neighbouring package still failing.

## Documentation

- The README records the 2026-09-30 Jev benchmark and the launchers' data
  modes (typryx#14), and gains a "Connect it to Wardryx" section (typryx#17).
  The install lines still name the previous tag; they move to this tag in a
  follow-up after the image is published, as for earlier releases (typryx#13).

## Upgrade notes

- Four new environment variables, all read only by `typryx wardryx-proxy` and
  all declared in `components.json`: `TYPRYX_PROXY_ADDR` (default
  `127.0.0.1:4330`; a non-loopback bind without `TYPRYX_KEYS` is refused like
  the service's own), `TYPRYX_PROXY_UPSTREAM` (required for the proxy,
  wardryx's base URL), `TYPRYX_PROXY_ASK_TIMEOUT_MS` (default 150, range 1 to
  5000, the most a slow typryx may add to one decision) and
  `TYPRYX_PROXY_TEMPLATE` (default `action.risk_class`; a choice template
  whose fields are only `tool`, `arguments` and `target`). An unusable proxy
  setting refuses to start and names the variable.
- The `serve` subcommand and every existing variable are untouched. The
  config code was refactored (`loadConfigAt`, `buildService`,
  `serveRuntime`) with every existing test left green.
- To use the proxy, point the caller's wardryx URL at it (TokenFuse reads
  `TOKENFUSE_WARDRYX_URL`). Each eligible decide request costs one ask, so the
  service's hourly cap governs spend; there is no circuit breaker.
- Without `TYPRYX_KEYS` asks are answered but the journal skips them, since
  there is no agent identity from a credential. On loopback the usual setup is
  no keys.
- A signal is only as good as the backend behind it. The `stub` backend's
  probabilities mean nothing; a real backend is a separate decision.
- A 0.3.0 deployment moves to 0.4.0 by moving the image tag.

## Not proven

- The proxy was not run in front of a real wardryx, behind a real TokenFuse
  broker, or with Jev, and no model call was made. It was run against a
  loopback stand-in for wardryx with the stub backend.
- The template's accuracy is the evalset's measurement, not this release's.
- TokenFuse's `tool_call` fields and `TOKENFUSE_WARDRYX_URL` were read from
  its source, not from a run.
- The `arguments` field passes as a nested object through the egress filter,
  but a live backend receiving a nested object in `state` was not exercised.
- A caller that must send `X-Typryx-Key` needs a way to add a header.
